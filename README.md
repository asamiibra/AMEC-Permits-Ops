# ProposalOps Build Weeks 1–9 / Integrity-Reconciled Baseline

ProposalOps is a modular-monolith foundation for a fictional engineering consultancy managing proposal and contract work in Qatar. The visible product model is AMEC Work, Proposals & Contracts, Issues, Notifications, and Operating Guide; legacy PermitOps identifiers remain compatibility-only implementation details.

> **THIS REPOSITORY CURRENTLY USES SYNTHETIC TEST DATA ONLY.**  
> **DO NOT ADD REAL QIDs, TITLE DEEDS, OWNER PERSONAL DATA, MINISTRY CREDENTIALS, OTPS, OR CLIENT PROJECT DOCUMENTS UNTIL THE APPROVED DATA-ACCESS / TEST-ENVIRONMENT DECISION EXISTS.**

## What is included

- FastAPI + SQLAlchemy modular monolith with explicit APIs.
- SQLite DEV/TEST fallback and native PostgreSQL 16 target-runtime validation; Docker Compose remains a convenience path.
- Synthetic office, users, projects, applications, discovery data, inquiries, RAID, audit trail, and deterministic correlation IDs.
- Separate local Synology-style filesystem, Excel workbook, and Permit Authority Simulator.
- React + TypeScript + Vite internal UI with dashboard, projects, document verification, conflict review, configuration, extraction spike, submission confirmation, discovery, business case, privacy, volume, inquiry, and RAID views.
- Tier 1 provisional configuration for field authority, document/attachment categories, requirements and dependencies, drawing metadata controls, and a local municipality interaction contract.
- Document intelligence foundation with content-hash deduplication, version and approval states, deterministic synthetic classification/extraction, source evidence, Arabic digit and identifier normalization, human verification, immutable correction history, and explicit audit events.
- Synthetic-only extraction spike with a real-document approval gate. Candidate metrics are labeled as candidate metrics and are not final verified-value metrics.
- No real external-system connections and no municipality submission method.
- Deterministic Week 4 readiness/package foundation and Week 5 assisted municipality preparation with snapshot/reconciliation, precheck evidence, attended-session state, and human handoff.
- Week 7 controlled findings, durable authority events, owned workflow tasks, provisional synthetic SLAs, retryable notification outbox, conservative deduplication, precheck/official-comment/portal-validation ingestion, and bilingual RTL operator UX.

## Run locally

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r backend/requirements.txt
make migrate
make seed
uvicorn backend.app.main:app --reload
```

In another terminal:

```bash
cd frontend
npm install
npm run dev
```

Open http://localhost:5173. The API is at http://localhost:8000/docs. The local synthetic authority simulator is served by the same backend under `/mock-authority` and is deliberately labeled as non-official.

## PostgreSQL 16 target runtime

The acceptance gate uses the existing `DATABASE_URL` convention. For the native Homebrew PostgreSQL 16 instance:

```bash
APP_ENV=TEST DATABASE_URL='postgresql+psycopg://<local-user>@localhost:5432/permitops_test' SYNTHETIC_ONLY=true make migrate
```

Docker Desktop is not the acceptance criterion. If it is unavailable, the Docker convenience path is technical debt; the required target runtime is PostgreSQL 16.

## Docker Compose

```bash
make up
make seed
```

This starts PostgreSQL, the backend, and the frontend. `make down` stops the stack. `make reset` removes the local database volume and recreates the synthetic environment.

## Tests

```bash
make test
```

Backend tests use an isolated SQLite database by default and honor an externally supplied `DATABASE_URL` for PostgreSQL regression. Frontend tests use Vitest where dependencies are installed.
